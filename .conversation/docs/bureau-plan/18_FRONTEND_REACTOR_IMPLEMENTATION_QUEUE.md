# Apex Atlas Frontend — Reactor Implementation Queue

**Status:** Active implementation queue  
**Date:** 31 August 2026  
**Authority:** subordinate to `16_FRONTEND_40K_MASTER_PLAN.md` and `17_FRONTEND_REACTOR_LIVE_GATE.md`

## Purpose

This file records the next implementation gates discovered while working against the actual frontend source. It is intentionally operational rather than aspirational.

## Gate 1 — truthful activity rendering

The Reactor UI may render a browser/search scene only when the Bureau event contains an actual recorded query or URL. A target name is context, never evidence that a query was issued.

Required event fields, when applicable:

- action/event id
- timestamp
- method
- status
- actor/provider
- actual query/tool input
- actual URL/source
- result summary
- evidence/source references

The UI may provide visual browser chrome, but the content inside that chrome must be derived from the event.

## Gate 2 — semantic action theatre

Different observable actions require different scenes:

- web search: search page/result surface
- browser/page fetch: browser/source surface
- registry: filing/registry surface
- domain: domain/RDAP/DNS surface
- social: public-profile surface
- graph: relationship/network surface
- LLM/tool decision: safe operational action surface
- case/evidence: evidence ledger/card update surface

The visual scene is presentation, not orchestration. The backend remains model-led.

## Gate 3 — safe live narration

The user should see what Apex is doing and what evidence changed, not hidden model deliberation. Recorded tool inputs may be displayed when they are safe and actually recorded. Hidden chain-of-thought must never be reconstructed from prose or inferred from target names.

## Gate 4 — mobile parity

Mobile must preserve the same event semantics as desktop while changing composition. It should prioritize:

1. current action
2. current source/evidence
3. target/entity context
4. recent action history
5. network/card detail on demand

A fixed seven-stage workflow rail must not imply that Apex follows a deterministic seven-step process.

## Gate 5 — provenance-first cards

Every visually prominent claim should be able to open its supporting source. Organization routes must remain organization routes; they must not be visually promoted into direct personal contact without evidence.

## Gate 6 — state completeness

The Reactor must have explicit states for:

- idle
- connecting
- active
- waiting for evidence
- pivoting
- evidence found
- contradiction
- blocked
- failed
- completed
- cancelled

Animations are subordinate to state. No animation may imply an action that did not occur.

## Gate 7 — performance and quota discipline

Streaming activity should be event-driven rather than generated by frontend timers. The frontend should not poll aggressively merely to create the appearance of activity. Provider/model telemetry should be sampled or aggregated where the user gains no additional truth from every individual heartbeat.

## Gate 8 — validation

The acceptance path is:

1. static contract
2. frontend build
3. provider-backed Bureau run
4. captured event stream
5. desktop render review
6. mobile render review
7. provenance audit
8. regression against known fake-query/fake-identity cases

A visually impressive Reactor that cannot demonstrate that its displayed research activity came from real events is a failed implementation.

## Current finding

The existing `BureauOpsStage` still contains a synthetic fallback that constructs `"<target> contact email phone"` when a search-like event lacks a recorded query. This violates Gate 1. A dedicated CI no-fabrication contract has therefore been added so this regression is now explicit rather than hidden.

The source fix must remove that fallback and allow the scene to show an honest `No explicit query recorded` state (or a non-browser semantic scene) until the backend supplies a real query.

## Immediate implementation order

1. Remove synthetic query fallback from `BureauOpsStage`.
2. Route search/browser scenes through `explicitResearchQuery` and `sourceList` from the shared Reactor semantic model.
3. Preserve recorded tool input separately from human-readable result text.
4. Add deterministic fixtures for search, browser, registry, domain, social, graph, contradiction, and blocked states.
5. Capture real Bureau events from a provider-backed run and compare rendered scenes with the raw event stream.
6. Add desktop/mobile screenshot review only after semantic truth passes.
7. Continue into entity-card, evidence-ledger, wealth visualization, and network/map surfaces.
