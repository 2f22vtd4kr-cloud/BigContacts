The biggest prompt bug
This is a genuine defect:
"email": "general org contact email or null"

That schema is used even for an HNWI/person target, despite the surrounding instructions saying:
Find PERSONAL direct contact information ONLY.

So the prompt is simultaneously telling the model:
1. Find Mariann’s personal/direct contact.
2. Return a “general org contact email.”
That can absolutely reduce extraction quality.
Why multiple models still produce poor persisted data
The models are not currently functioning as a true ensemble.
1. The providers search independently, but their outputs are not reconciled intelligently
Perplexity, Gemini, Tavily, and Exa each return results. But the system mostly:
* collects their fields,
* records provider evidence,
* scrapes some URLs,
* then promotes only values passing strict persistence gates.
There is no meaningful “Gemini found X, Perplexity found X, Tavily found X—therefore this is a high-confidence candidate” reconciliation layer.
2. The system refuses useful but non-perfect results
For example, Google/Gemini may find:
Mariann Staxrud Utstumo — LinkedIn profile
mariann@company-domain.no

But the pipeline may reject or downgrade it if:
* the email is not explicitly visible in the cited text,
* the source URL is not attached directly to the person,
* the domain is not clearly associated with the person,
* only one provider returned it,
* it resembles a company or role-based mailbox,
* it cannot be independently corroborated.
That is appropriate for verified contact promotion, but it is too strict for the initial candidate discovery layer.
We need to preserve the result as:
“Potential contact candidate — requires review”
instead of treating it almost like:
“No usable contact found.”
3. Search results are recorded with weak attribution
The provider-level contact writes in web-enricher.tsoften record contacts without explicit person-level attribution metadata. For example, a result from Gemini or Perplexity is recorded generically rather than as:
{
"scope": "person_candidate",
"personName": "Mariann Staxrud Utstumo",
"provider": "gemini",
"sourceUrl": "..."
}

That makes later quality checks unable to distinguish:
* a contact for Mariann,
* a company switchboard,
* an organization mailbox,
* a contact belonging to another person mentioned in the article.
The safe behavior is to downgrade everything. The result is safe, but the yield is terrible.
4. Groq is not cross-checking the other models
For Tavily and Exa, the flow is:
Tavily/Exa search → excerpts → one Groq extraction call

Groq is not comparing Gemini, Perplexity, Tavily, and Exa answers. It is extracting from whichever text it receives.
Likewise, extractWithAI() returns the first successful Groq/OpenRouter extraction. It does not ask multiple models to extract the same source text and then reconcile disagreements.
So “multiple trained LLMs” currently means:
multiple independent search attempts
—not:
multiple models jointly verifying and merging every discovered contact.
5. The current pipeline prioritizes evidentiary purity over discovery yield
The design has strong safeguards against invented emails, but it currently collapses these states too aggressively:
not found
found but uncertain
found with one source
found with source but attribution uncertain
found and independently corroborated

Those should be five separate states. Right now, several of the first four end up looking like “no useful contact.”
The contradiction in our metrics
The database currently says:
* 10 direct-contact candidates
* 13 contactable records
* 0 independently supported contact rows
* 0 verified direct contacts
* 1 qualified hot lead
That does not mean:
“The app can only find one useful person.”
It means:
“Only one record currently passes the app’s strict promotion rules.”
That is a data-promotion problem, not a fair measure of search capability.
And yes: comparing this to asking Gemini or Google directly exposes the gap. A direct Gemini answer is usually willing to say:
“This appears to be the person’s professional email / LinkedIn / company route.”
Our app currently says:
“Unless I can prove the contact is personal, directly cited, correctly attributed, and independently corroborated, I will not promote it.”
That is a valid compliance posture, but it is the wrong default if the goal is high-yield OSINT discovery.

1. Discovered candidate
2. Source-linked candidate
3. Attribution-reviewed candidate
4. Independently corroborated
5. Verified direct route
