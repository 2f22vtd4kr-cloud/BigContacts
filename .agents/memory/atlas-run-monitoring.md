---
name: Atlas run monitoring
description: Durable safety rule for bounded Atlas runs and truthful stalled-job telemetry.
---

Atlas runs can remain marked `running` while a provider-backed discovery source is stalled and the phase message does not change. Any run must be monitored for message/progress freshness, not only the active-job lock. Single-target mode is the safe way to finish one entity end-to-end: it skips discovery, registry ingestion, and global backfills while retaining the target-scoped enrichment/research journey. Continuous background mode is an explicit user choice; when requested, persist `ENABLE_AUTO_PIPELINE=true` and avoid restarting the API while an active Atlas run owns the process. Cancellation must be cooperative: clearing the active slot has to prevent the worker from entering the next phase or rewriting the job as active.

**Why:** A controlled re-enrichment run remained on the same Phase 1 discovery step for more than two minutes while the Reactor correctly showed active status; without a freshness check, the UI made a hung provider call look like productive work.

**How to apply:** Use `singleTargetId` for exact target work, bounded discovery-first runs for controlled ingestion, or the persistent scheduler when the user explicitly wants Atlas continuously active. Record the last progress/message change, surface stale-step age in status, and provide a safe cancellation path before allowing another provider-heavy phase to continue. Check active-job ownership at phase, source, and entity boundaries; provider failures should remain fail-closed and visible in the run summary. Keep a bounded per-target deadline so a provider-heavy target cannot block the sequential queue; timeout outcomes must remain review-only with `cookedAt` unset and an explicit retry action.
